# 后端开发经历证据工作流

本参考用于处理 Java 后端、Python 后端、微服务、AI 应用开发、平台研发和全栈偏后端经历。它把项目拆成业务场景、系统边界、个人技术动作、工程结果和可追问证据，避免把技术名词堆砌成能力，也避免把团队成果或方案设计写成个人上线结果。

## 何时使用

当目标岗位或材料出现以下信号时使用本工作流：

- Java、Python、Spring Boot、Spring Cloud、微服务；
- API、数据库、缓存、消息队列、并发、事务、一致性；
- 性能优化、慢 SQL、压测、监控、故障排查；
- Agent、MCP、Tool Calling、RAG、模型 API 和 AI 应用工程化；
- 权限、鉴权、幂等、重试、补偿、灰度或部署；
- 需要区分个人负责模块、团队系统能力和技术方案结果。

## 六层事实拆解

先记录原始事实，再生成简历句子：

| 层级 | 需要回答的问题 | 常见证据 |
| --- | --- | --- |
| 业务场景 | 系统解决什么问题？服务什么业务流程？ | 项目说明、需求、业务流程 |
| 系统边界 | 系统包含哪些服务、模块、数据和外部依赖？ | 架构图、模块目录、接口文档 |
| 个人动作 | 个人具体负责什么模块、接口或链路？ | 代码、PR、commit、任务记录 |
| 技术决策 | 为什么采用这个方案？有哪些替代方案和取舍？ | 技术方案、评审记录、实验结果 |
| 工程结果 | 功能、性能、可靠性或扩展性结果是什么？ | 测试、日志、监控、上线记录 |
| 个人边界 | 哪些由个人完成，哪些是团队能力或现成框架？ | 分工、提交记录、用户确认 |

## 结果性质标签

每个结果至少标记一种性质：

- `功能交付`：完成接口、模块、业务链路或可运行功能；
- `性能结果`：响应时间、吞吐量、SQL 耗时、Token 占用等有对比基准的结果；
- `可靠性结果`：幂等、重试、补偿、故障恢复或数据一致性能力；
- `工程结果`：组件复用、配置化、扩展性、维护性或接入成本变化；
- `阶段结果`：原型、技术验证、测试通过、内部试用或部分上线；
- `方案设计`：完成架构、技术方案或实验，但没有证明已经上线；
- `团队结果`：由多人共同完成，个人表述必须回到负责模块。

不要把“支持”“具备”“设计”自动改写成“上线”“实现提升”或“带来收益”。

## 技术主张核验

### 框架和工具

仅出现技术名词时，只能写“使用过”“接触过”或“项目采用”。要写“熟悉”“掌握”，至少需要能够说明：

1. 在什么场景使用；
2. 个人如何配置、调用或扩展；
3. 遇到什么问题；
4. 如何验证结果。

例如，项目使用 Spring AI 不自动等于掌握 LangChain；调用 Redis 不自动等于掌握缓存设计；使用 RabbitMQ 不自动等于掌握消息一致性。

### 架构和设计

“设计架构”“负责核心模块”“主导方案”等强表述，至少要能回答：

1. 设计边界是什么；
2. 个人做了哪些决策；
3. 关键取舍是什么；
4. 方案如何被代码、测试或运行结果验证。

证据不完整时，降级为“负责模块实现”“参与方案设计”“完成技术验证”。

### 指标和结果

每个数字需要记录：

- 测量对象；
- 对比基准；
- 测试或运行条件；
- 时间范围；
- 结果性质；
- 个人贡献边界。

例如，“响应时间从 6700ms+ 降到约 150ms”可以写入简历，但面试前应准备优化前后的 SQL、索引变化、数据规模和测量方式。“效率成倍提升”如果没有基准和测试结果，应改为描述并行处理机制，不保留该数字。

## 后端项目简历句式

优先使用以下顺序：

```text
业务问题 -> 技术动作 -> 关键取舍 -> 交付对象 -> 验证结果 -> 个人边界
```

通用模板：

> 针对【业务问题】，负责【模块或链路】，通过【技术方案】处理【关键难点】，交付【接口、组件、任务或系统能力】；经【测试、日志、监控或上线记录】验证，达到【结果】。

没有结果指标时，使用可核验的交付结果：

> 围绕【业务流程】，负责【模块】，实现【功能和关键机制】，并通过【测试、代码评审或运行验证】完成交付。

## 常见技术主题的证据问题

### 性能优化

- 慢在哪里：SQL、网络、锁、序列化、模型调用还是线程池？
- 如何定位：日志、链路追踪、执行计划、监控还是压测？
- 改了什么：索引、查询、缓存、批处理、并发模型还是调用策略？
- 如何验证：优化前后数据、测试条件和回归结果是什么？

### 并发与一致性

- 共享资源是什么？
- 竞态条件如何产生？
- 使用了锁、原子操作、幂等、版本号还是消息补偿？
- 异常和重试会不会重复扣减或重复处理？

### 消息与异步链路

- 消息由谁生产、谁消费？
- 如何处理重复、丢失、顺序和失败？
- 是否有任务表、重试、死信或人工补偿？
- 个人负责的是生产端、消费端、补偿机制还是整体方案？

### AI Agent 工程化

- Agent 解决的具体业务或开发流程问题是什么？
- 个人负责模型调用、Prompt、工具协议、上下文、记忆、权限还是流程编排？
- 哪些能力由框架或模型提供，哪些是个人实现？
- 是原型、技术验证、内部试用还是正式生产？
- 指标是 Token、延迟、成功率、人工反馈还是其他结果？

## 责任动词选择

| 证据强度 | 建议表述 | 风险较高的表述 |
| --- | --- | --- |
| 有明确代码和交付物 | 实现、完成、搭建、落地 | 主导整体架构 |
| 负责连续模块并能解释设计 | 负责、设计、改造、推进 | 独立负责全系统 |
| 参与方案或协作开发 | 参与、协同、支持、共建 | 主导、Owner |
| 只有技术接触或口述 | 使用过、了解、接触 | 精通、熟练掌握 |
| 只有方案或实验 | 设计、验证、探索 | 上线、实现收益 |

## 面试追问清单

生成每条项目表述后，至少准备以下问题：

- 你负责的代码边界在哪里？
- 为什么选择这个技术方案？
- 如果不使用这个框架或中间件，替代方案是什么？
- 最难排查的问题是什么？如何定位？
- 如何验证功能、性能和数据正确性？
- 异常、重试、并发和边界条件如何处理？
- 哪些是个人结果，哪些是团队结果？
- 这项能力能否迁移到目标岗位的业务系统？

## 交付前检查

- 每个技术主张都能回到项目、代码、测试、日志、文档或用户确认；
- 每个数字都有基准、条件和结果性质；
- 团队能力没有被改写成个人能力；
- 方案设计没有被写成已经上线；
- 框架名称没有替代真实技术动作；
- 项目描述同时包含业务场景和工程动作；
- 简历中的每条重点内容都能被用户用具体代码路径、接口、数据流或排障过程展开。
